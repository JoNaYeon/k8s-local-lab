# 쿠버네티스(Kubernetes)란?

## 한 줄 요약

**쿠버네티스는 컨테이너를 자동으로 배포하고, 관리하고, 스케일링해주는 시스템이다.**

## 우리가 쿠버네티스를 쓰는 이유

### 지금까지 배포하던 방식 (systemd)

현재 Health-Mentor는 이렇게 운영한다:

```
서버 1대 → systemd로 gunicorn 프로세스 실행 → 끝
```

이 방식의 문제:

| 문제 | 설명 |
|------|------|
| 서버가 죽으면? | 수동으로 접속해서 재시작해야 한다 |
| 트래픽이 늘면? | 서버를 추가하고, 로드밸런서를 수동으로 설정해야 한다 |
| 버전 업데이트? | 서비스를 중단하고 코드를 교체해야 한다 (다운타임 발생) |
| 서버 환경이 다르면? | "내 컴퓨터에서는 되는데..." 문제가 생긴다 |
| 여러 서비스를 운영? | 각 서버마다 일일이 설정해야 한다 |

### 쿠버네티스 방식

```
선언: "이 앱을 3개 복제본으로 실행하고, CPU 70% 넘으면 5개로 늘려줘"
→ 쿠버네티스가 알아서 한다
```

| 기능 | 쿠버네티스가 해주는 것 |
|------|----------------------|
| 자동 복구 | 컨테이너가 죽으면 자동으로 새로 띄운다 |
| 자동 스케일링 | 트래픽에 따라 복제본 수를 자동 조절한다 |
| 무중단 배포 | 새 버전을 하나씩 교체해서 다운타임 없이 업데이트한다 |
| 환경 통일 | Docker 이미지로 어디서든 동일한 환경을 보장한다 |
| 선언적 관리 | YAML 파일로 "원하는 상태"를 선언하면, 쿠버네티스가 그 상태를 유지한다 |

## 비유: 쿠버네티스 = 음식점 매니저

```
당신 (개발자): "이 요리(앱)를 항상 3명의 요리사(Pod)가 만들고 있게 해줘.
               손님이 몰리면 5명까지 늘려도 돼."

쿠버네티스 (매니저):
  - 요리사가 쓰러지면 → 새 요리사를 즉시 투입
  - 손님이 몰리면 → 요리사를 추가 투입
  - 레시피가 바뀌면 → 한 명씩 교대하며 새 레시피로 전환
  - 어느 지점에서든 → 동일한 레시피(Docker 이미지)로 동일한 음식을 제공
```

## 핵심 철학: "선언적(Declarative)" 관리

기존 방식 (명령형, Imperative):
```bash
# 하나씩 직접 명령
ssh server1 "pip install -r requirements.txt"
ssh server1 "systemctl restart myapp"
ssh server2 "pip install -r requirements.txt"
ssh server2 "systemctl restart myapp"
```

쿠버네티스 방식 (선언적, Declarative):
```yaml
# "원하는 상태"를 YAML로 선언
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 3          # "3개 실행해줘"
  template:
    spec:
      containers:
        - image: myapp:v2  # "이 이미지로"
```

```bash
kubectl apply -f deployment.yml  # 한 번 실행하면 끝
```

**쿠버네티스는 이 YAML을 읽고, 현재 상태가 원하는 상태와 다르면 자동으로 맞춰준다.**

## 컨테이너(Docker)와 쿠버네티스의 관계

```
Docker    = 앱을 상자(컨테이너)에 포장하는 도구
Kubernetes = 수많은 상자를 관리하는 물류 시스템

Docker만 쓰면: 상자를 하나씩 직접 옮겨야 한다
+ Kubernetes: 상자를 어디에 놓을지, 몇 개 만들지, 고장나면 어떻게 할지 자동으로 처리
```

## 우리의 전략: 로컬 k3s → 서버 표준 k8s

쿠버네티스에는 여러 "배포판"이 있다:

| 배포판 | 특징 | 용도 |
|--------|------|------|
| **kubeadm** | 공식 설치 도구, 표준 k8s | **프로덕션 (우리의 서버 목표)** |
| **k3s** | 경량 k8s, 단일 바이너리, CNCF 인증 | **로컬 테스트 (지금 이 레포)** |
| minikube | VM 기반, 무겁지만 학습 편의 기능 | 로컬 학습 |
| kind | Docker 안에서 kubeadm 실행 | CI/CD 테스트 |
| EKS/GKE/AKS | 클라우드 관리형 | 클라우드 프로덕션 |

### 왜 로컬에서는 k3s(k3d)를 쓰는가?

1. **가볍다** — macOS에서 Docker만 있으면 수 분 안에 클러스터 생성
2. **빠르다** — 리소스 소모가 적어 노트북에서도 쾌적
3. **CNCF 인증** — 표준 k8s API와 100% 호환. kubectl 명령, YAML 매니페스트 모두 동일
4. **k3d** — k3s를 Docker 컨테이너 안에서 실행하는 래퍼. 멀티노드 클러스터를 손쉽게 구성

### 서버 전환 시 뭐가 달라지는가?

```
로컬 (k3d/k3s)                  서버 (kubeadm)
──────────────────              ──────────────────
Docker 컨테이너 안에서           베어메탈 서버에서
k3s가 실행                      kubeadm으로 설치

공통점: kubectl, YAML 매니페스트, Pod/Service/Ingress 전부 동일
차이점: 내부 컴포넌트 구성 (etcd 분리, 컨트롤 플레인 HA 등)
```

**핵심: 우리가 작성하는 매니페스트(YAML)와 kubectl 사용법은 k3s든 kubeadm이든 동일하다.**
로컬에서 연습한 모든 것이 서버에서 그대로 적용된다.
